# M07 运行器决策：继续使用据理持久运行器

日期：2026-09-22。状态：当前阶段采纳；不排除后续根据新需求重新评估。

## 决定

继续使用 `DurableRunner`、`RuntimeStore` 和任务状态作为唯一业务执行权威。正式包不增加 LangGraph、LangChain 或多 Agent 调度，也不提供运行器切换开关。M08 的场景验证都在这一套实现上进行。

保留 [独立实验](../../experiments/m07_langgraph/README.md)，用于复核本次结论，不将实验原型当作另一套可供用户部署的实现。运行时源码、公共合同、正式依赖和数据库迁移均保持 M06 版本。

## 比较的范围

对照是有边界的调度实验：基线直接调用现有运行器；候选由 `StateGraph` 调度同一个运行器动作。两者使用同一份合成任务的数据库副本、相同假模型、资料、提示上下文、网关、工具和预算策略。候选不重新实现身份授权、检索、证据回读或业务事务。

另外单独验证 LangGraph 原生 SQLite 检查点和 `interrupt` 跨进程恢复。这样既验证框架提供的能力，也测量接入现有业务账本时的额外协调问题。没有测试全量迁移为 LangGraph 原生状态的方案，没有据此证明其他集成方式不可行。

验证使用 LangGraph `1.2.9`、LangGraph checkpoint `4.1.1`、SQLite saver `3.1.1` 和 langchain-core `1.5.1`。其他关键版本与命令见实验目录。版本记录不等于完整传递依赖锁定。

## 观察结果

24 项实验测试与原有 182 项回归全部通过，均使用合成资料；没有真实模型分析或生产数据库操作。[结果记录](../../experiments/m07_langgraph/results.json)保存测试汇总和测试环境版本。

| 检查 | 现有运行器 | LangGraph 调度候选 |
|---|---|---|
| 追问、回答、检索、回读、完成 | 6 个动作，4 次假模型调用 | 同样的请求、结果、计数和事件种类 |
| 已提交动作之间重建对象 | 从据理账本继续，预算不重置 | 委托同一账本继续，预算不重置 |
| 取消、令牌撤销、资料撤下后的迟到响应 | 拒绝提交结果 | 据理机制继续拒绝；并非框架自动提供 |
| 旧动作计数与并发请求 | 不变成新动作，不重复调用 | 同一动作账本继续拦截 |
| 未知动作结果和预算 | 失败停止，保留预留预算 | 同样停止，没有增加自动重试 |
| 未回读的事实引用、越权工具 | 拒绝 | 网关与引用校验继续拒绝 |
| 独立中断恢复 | 追问已保存为业务 pending 状态 | 原生 SQLite `interrupt` 能恢复，中断节点会重入 |
| 业务提交后进程立即退出 | 新进程读取已提交的 pending 状态 | 图投影尚未提交，恢复遇到旧计数，需要显式协调 |

正常流程比较包含四次完整 `ModelRequest`，以及最终任务状态、结果、预算计数和事件种类；排除事件时间、事件 ID 与实测耗时，不做性能排名。

### 中断恢复确实可用，但副作用仍需明确处理

实验在 `interrupt` 前执行一次合成数据库写入，结束进程，再在新进程回答。回答成功，节点入口计数从 1 变为 2。这符合官方说明：恢复会从中断节点开头重新执行，中断前的操作必须能安全重复执行。它不是本次发现的框架缺陷。[LangGraph interrupts 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

### 图检查点与业务提交之间存在集成成本

故障实验先让据理提交第一个动作，再在图节点返回之前强制结束进程。使用 SQLite saver 与 `durability="sync"` 后，新进程仍观察到：据理已是 `pending`、动作数为 1，而图保存的预期动作数仍为 0。

图恢复时再次进入节点，据理返回 `stale_runtime_version`，未执行第二次模型调用。测试随后读取据理的权威状态、提交回答，并建立新调度继续到完成；这不是原图自动修复。节点内偷偷刷新动作计数会把旧请求变成新的执行意图，因此本原型不这样做。

LangGraph 同步检查点保证其自身检查点的保存时序，不能使另一个数据库中的业务事务自动与节点返回成为一次原子提交。官方也说明了检查点边界、持久化模式和重放行为。[LangGraph checkpointers 文档](https://docs.langchain.com/oss/python/langgraph/checkpointers)

如果以后接入，需要设计明确的提交回执、动作幂等结果读取或共享事务适配，验证崩溃窗口与撤权行为；不能把框架检查点直接视为据理业务完成记录。现有运行器也不能保证外部调用恰好执行一次：调用完成但未提交的未知结果仍会失败停止。

## 为什么当前不迁移

1. 当前是有预算的串行动态行动循环：模型可以提问、请求工具或给出结果，不需要为每种场景硬编码流程图。场景通用性主要由资料角色、工具协议、分析指导和结果 schema 提供。
2. 在保留已有边界的候选中，LangGraph 没有减少动作授权、预留、迟到响应检查、证据凭证等业务代码；启用检查点还需额外处理图投影与账本的协调。当前没有足够明确的分支编排需求抵消这部分工作。
3. 新增框架会扩展依赖维护面。测试版本的 LangGraph 声明了 langchain-core、checkpoint、prebuilt、SDK 等依赖；SQLite saver 另有依赖。独立实验安装这些包，普通据理安装则不需要。

这不是速度、模型质量、长期维护工时或所有架构方案的综合胜负判断。本轮没有性能压测、真实模型评测，也没有实现完整 LangGraph 原生替代运行器；结论只支持“当前阶段无需迁移”。

LangChain 暂不引入：现有模型和工具端口已满足当前接入范围。多 Agent 也暂不引入：尚无已验证的独立职责与并行需求；通用场景平台不要求多个 Agent。后续若引入，需要能展示其收益，并继续服从同一资料权限、预算与结果提交规则。

## 什么时候重新评估

- 已有具体场景需要可维护的多分支、并行汇合或多级人工审批，现有串行运行器出现可复现的维护困难。
- 需要图可视化调试、子图复用或长流程编排，且能用真实用例说明收益。
- 新适配方案能在保留单一业务状态权威的同时，减少代码或操作成本，并通过本轮故障用例与现有回归。
- 多 Agent 方案在相同资料、任务与预算下，表现出可核验的质量或耗时收益，再单独决定是否采用。

如果重新评估，先定义业务状态权威、检查点和外部副作用的关系，再实现适配器；不会因选用框架而改变核心场景接口。
