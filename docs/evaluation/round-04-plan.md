# E04：明确分析结果与追问的输出边界

日期：2026-10-02。问题：JULI-002、JULI-003、JULI-004；状态：本轮实施与三题实测完成，仍有追问/回读问题。下方“修改前的计划”为代码修改前记录，实际改动和失败另列。用户授权进入下一步，继续原三道合成题，累计费用上限5元，保留全部旧试次，不推送或发布。

## 怎么发现

E03三题均已检索并完整回读原文，最终却把输入资料目录、问题、日期写进字符串字段 `scenario_payload_json`。外层JSON可解析，场景校验因缺少 `summary` 且包含额外字段而拒绝。两道应追问题只在原始分析中罗列待确认事项，没有生成有效 `clarification` 或进入 `pending`。这是实际输出协议与控制选择失败，不能靠删除场景要求或提前给出回答卡来修复。

原三题输入、场景和金标冻结不变；E03三题9次响应、14次工具轨迹及各源码指纹保留。修改前211份源码与文档另存本地 `.local/e04-baseline/`。

## 修改前的计划

1. 引入清晰的模型侧分析结构：`kind=analysis`、任务ID、证据块、原生对象形式的场景结果；框架严格解析后确定性序列化为既有内部 `AnalysisResult`。避免要求模型额外构造转义JSON字符串，不改变公开结果结构、数据库、场景schema或引用验证。
2. 保留旧严格分析格式的读取兼容，错误旧输出依旧拒绝；混用两种字段或缺少必填字段不得自动修复。新增结构中的引用、任务ID、范围和场景要求仍走原校验链，不增加供应商特有接口或模型自动重试。
3. 合并相互分散的终态指令，在持久入口明确“继续取证 / 缺少决定性信息则追问 / 信息足够则分析”选择。展示互斥结构，强调场景结果由场景schema定义，资料目录是输入。追问只针对资料与已收到回答仍未解决的关键事项，回答后区分用户自述与文件依据。旧内存入口不宣称支持追问。
4. 提示模型核对建议和限制段与已读资料的一致性，不擅增门槛、不把已说明信息重新当成未知；JULI-004仍须依据实测结果判定，不保证提示词能根除事实错误。
5. 新E04试次只继承剩余额度：E02未知预留0.160768元 + E03费用上界0.120292元均保留。E04子上限4.718940元，至多26次新调用，整个授权最多36次。旧账本只读，旧目录不覆盖；新目录有独立试次及来源哈希。

## 验收条件与回归风险

- 新对象结构的正确分析经同一任务/场景/引用校验提交；旧正确输出仍可用，E03原始错误输出重放仍拒收。
- 无效/混合结构、任务ID不符、非法场景字段、未回读或越权证据仍拒绝；不能把错误响应转换成合法结论。
- 有效追问能进入pending，答复后可恢复完成；用无关合成场景测试协议控制，不在测试中硬编码三题正确结论。
- 模型配置加入新的响应协议指纹，旧任务不得无声切换协议；不改历史迁移DDL。
- 完整离线回归通过，再按同一配置、同一三题各跑一个新试次。仅在真实pending问题出现后提供相关回答卡事实，保存原始响应、追问、回答、用量和逐项辅助诊断。
- 输出过长、无限追问、schema未遵从、证据引用失效均作为失败保留，不能静默重试或降低门槛。API调用未知则停批次保留预留。

## 具体怎么修改

- 新增 `application/model_response.py`：模型返回 `kind=analysis` 与原生 `scenario_payload`；严格转换为既有内部字符串字段。原严格格式仍可解析，错误/混合结构不修补。持久入口的输出schema为analysis/clarification互斥结构，旧内存入口仅analysis。
- 修改 `application/context.py`、`runtime.py`、`model_session.py`：统一终态提示，区分目录输入与分析结果，说明先回读、缺决定性信息则追问等待、收到答复后更新判断。新协议标识进入模型配置指纹，旧已开始任务不能悄悄换协议。公共结果合同、权限校验、数据库DDL和默认预算不变。
- 新增35项合同检查、19项持久集成检查、32项累计评测账本检查；覆盖无效结果、引用、权限撤销、追问恢复、旧格式、场景schema引用作用域及预算丢失/冲突停止。
- 新增评测入口 `examples/quality_eval/revision_smoke.py`，只读校验旧证据，再创建独立试次和批次外初始化标记。没有给正式运行器增加供应商依赖；不修改冻结场景或答案。
- 没有引入多Agent运行架构、LangChain/LangGraph替换、生产部署或新场景。协作Agent仅参与开发和独立评审，不是产品的新运行架构。

### 失败尝试与纠正

1. 第一版提示词过长：合同及旧运行器组合检查79通过、1失败；四调用演示累计需要40744输入单位，超过原32000预算。保留首版上下文源码，压缩重复说明，不增加额度。
2. 压缩后目标检查18通过、2失败：演示仍需32816单位，另一个新增测试只匹配固定提示词措辞。移除该脆弱文本断言，保留schema和流程断言。第二次压缩19通过、1失败，演示32124单位；再次简化后演示通过。
3. 第一轮完整测试408通过、1失败：更长的既有HTTP追问样本仍超过原预算。仅删除模型schema中非校验用途的 `title` 注释，保留properties名称、$defs、$ref、约束和默认数据；再跑35项合同与两个既有流程，共37项通过。
4. 最终完整测试 **409通过、0失败、2项既有依赖弃用警告**，76.82秒。最初失败XML和最终XML分别保留，重叠的针对测试不能相加当测试总数。
5. 实测汇总首次用 `answer-*.json` 把答案原件与提交回执都计为回答，错报两次。改为只统计数字编号的答案文件，并核对pending事件和模型request，实际一次。首版汇总保留为检查证据；这是汇总器计数问题，未改模型轨迹或增加模型调用。

本地过程文件在 `.local/e04-checks/`：`attempts.json`、`context-first-attempt.py`、两份测试XML、原响应重放结果与首版汇总。修改前211份文件保留在 `.local/e04-baseline/`。
