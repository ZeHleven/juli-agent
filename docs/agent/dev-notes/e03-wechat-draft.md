# API 回了 200，我的 Agent 却还没开始分析

本地草稿，未经发布。素材来自据理合成岗位案例，不含真实个人资料。

我给据理准备了第一套资料分析测试：让它结合岗位说明和个人背景，判断是否适合投递。

第一次真实调用很快收到了服务返回。可它还没读到资料，就停了。

问题出在一个我之前收得太窄的接口约定。模型返回了两次检索请求，还带了一句说明；而据理当时只接受一个工具请求，并且不允许同时带说明文字。

收到回应，和系统能把回应接下去，是两回事。那一轮还没有进行原文检索，也没有得出分析结论，所以我把它记为协议兼容失败，没有给模型的研判能力打零分。

这次修复，我保留了模型的一整条回复。它可以提出最多八个工具请求，但系统仍然逐个执行：先检查完整列表，再逐项检查权限、资料版本和预算。一个请求失败，后面的请求就停下；已经执行过的请求不会因为重新加载运行器而再执行一次。

说明文字也保留下来，作为对话的一部分。它不会被当作最终分析结果，更不会被当作新的系统指令。

旧的失败记录没有删。修复前的源码、原始返回、离线定位过程和费用预留都留在本地。后续试次仍共用五元上限，之前那次未结算的预留也继续算在里面。

这轮完整离线测试通过了323项，包括消息是否完整、多个工具的执行顺序、撤权后停止、预算不足、中途失败和恢复后不重复执行。过程中还发现了旧单工具流程的一处预算边界回归，修正后才重新跑完整测试。

这些结果证明接口和执行流程通过了相应检查。接着，我用相同版本跑了三道真实模型测试：资料充分的岗位匹配、缺少出勤信息的岗位匹配，以及两份方案互相冲突的参与判断。

这次三题都成功检索并读到了完整原文，但最终通过数是0/3。模型把输入资料目录填进了本应装分析摘要的结果字段，三题都被结构校验拒收。不能因为原始文字里有一些分析，就把任务记作成功。

逐段看原始回答，还有两个具体问题。第一道题的资料已经说了可以每周到现场三天，模型前面也引用了这句话，后面却又称这项偏好“没有记录”。第三道题在主要分析中写对了2025年的验收日期，末尾又写成了2026年。两道需要追问的题虽然列出待确认事项，却没有真的停下来等待回答。

这些问题是在读到正确资料之后出现的，所以需要分别修复结果格式、追问流程与全文事实一致性。离线测试通过，不能替代真实任务验收。本轮9次模型调用按保守价格计入约0.12元，原始回复、失败结果和旧费用预留都保留下来了。

我想记录的不只是“又加了一个功能”，也包括：哪里失败了，为什么改，改完之后究竟验证到了哪一层。
