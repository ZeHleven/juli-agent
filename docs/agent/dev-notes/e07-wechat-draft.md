# 据理开发笔记：把问题写进报告，还不算真的问过

本地草稿，未发布。材料来自合成评测；读者版不包含任何真实求职者或企业资料。

上一轮测试里，据理发现了一件影响判断的事：一份岗位要求每周到现场办公，但申请人的背景资料没有写能否到岗。

它确实发现了这个缺口，还把问题列在报告里。可任务已经结束了，页面没有进入等待回答的状态。对使用者来说，这两种体验差别很大：我需要的是有机会补充信息，再得到调整后的分析。

这次我给普通分析出口加了一个明确声明：还有没有会影响结论、需要用户回答的问题？有，就暂停等回答；没有，才提交最终结果。待确认的分析还会经过原来的来源与引用校验，不会因为叫“候选”就放宽要求。

用户说“暂时不知道”，也应该允许继续讨论有条件的结论。不能为了追问而一直追问。报告里的可选核验建议，也不必全部变成阻塞问题。

修复期间还遇到一个小回归：提示多写了一点，原来的短流程就超出了默认输入额度。最后压缩了重复说明，保留原有预算和验证规则。失败过程也留下来，方便以后复查。

现在验证的是代码能否按这个约定工作。它还不能证明模型每次都能发现关键未知，也不能保证模型不会把“还有问题”错误地写成“已经就绪”。这些要继续用真实模型测试，而不能拿脚本预设的正确回答当成绩。

本轮没有发起新的API调用，也没有增加预算。下一次，我想重点验证：该问的时候会不会真正问出来，已经回答的事情会不会反复问。
