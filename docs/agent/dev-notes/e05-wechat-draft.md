# 我给据理多加了一层审查，真实测试却从2/3退到了0/3

本地公众号草稿，未发布。本文记录据理 E05 的三组合成评测，不含真实求职者或企业资料。数字表示本轮流程完成数，不是准确率。

上一轮，据理的三道测试题完成了两道。剩下那一道，模型知道“还缺一项关键信息”，却没有真正停下来问；它也没有回读原文，就直接交了分析。

所以，这轮我想把“该读的时候读，该问的时候问”变成更明确的流程。

原来的方式，是期待模型自己安排好检索、阅读、追问和分析。这次试验中，我让它先交一份草稿。草稿不能直接成为用户看到的正式结果。框架根据草稿选择的引用，安排实际原文回读；读完后，再单独问模型：还有没有一项未解决的信息，会改变这次判断？

如果有，就提出问题，等待用户回答。收到回答后再审查一次，允许继续，才生成最终分析。

这看起来把步骤拆清楚了。但真正跑起来，结果并没有按我希望的方向走。

**这轮三道题，一道也没有完成。上轮是2/3，这轮是0/3。**

有一部分流程确实起作用了。

上一轮失败的那道岗位匹配题，这次先交出了合法草稿。框架随后回读了两份原文，模型也真正发起了追问，问申请人能否接受要求的现场出勤。我等问题出现之后，才按照事先冻结的回答卡补充事实，没有提前把评分要求或者答案塞给模型。

它的问题还不够聚焦：除了关键出勤条件，又问到了城市和入职安排。这也是需要记录的用户负担。

收到回答后，模型通过了审查，开始生成最终分析。问题就出在这最后一步：它把用户刚刚回答的内容标成了需要文档引用的“事实”，引用列表却是空的。结果结构校验拒收，任务失败。

这不意味着用户的回答没有价值。用户陈述可以用于判断，只是需要清楚标明它的来源，不能把它装进“已有原文证据支持”的类别。

到这里，取证和追问这部分得到了真实验证，但完整任务仍然没有做完。我不能因为前半段终于走通，就把这道题算成成功。

另外两道上轮完成的题，这次也失败了，而且都还没走到新加的审查阶段。

资料充分的岗位匹配题，模型做了两次检索、两次回读，随后在草稿最外层多写了一个格式不允许的 `trust` 字段，把输入资料的信任标记混入了输出。它没有符合约定的结果结构，草稿被拒收。

方案冲突题在更早的位置出错。模型把三个检索请求和一个读取请求放进同一批，读取时却把文件版本编号当成了证据编号。两种编号对应不同的对象，读取因此失败；没有形成可供审查的草稿，也没有真正追问。

这两个问题，新加的审查阶段都没机会处理。它们也提醒了我：把中间的某一步设计清楚，不代表入口、出口和整条流程就一起可靠了。

这轮还有一个容易让人误会的数字：502项离线测试全部通过，运行时有两项既有依赖警告。

这些测试验证的是流程约束：草稿不会提前交付，回读凭证确实存在，追问后能够恢复，权限被撤销时会停止，预算不会被重置，未知调用不会被自动重试。它们很有必要，但不能替模型保证每一次都选对工具参数、填对字段、分清用户陈述和文档事实。

离线测试通过、真实题目失败，可以同时发生。两份记录都应该留下。

目前，这个新模式仍然需要部署者显式开启，默认关闭。我还没有足够证据把它描述为一次成功升级。三题各跑一次也不足以隔离随机性，不能断言所有退步都由某一条提示或某一个新增步骤导致。

下一步需要从这次留下的失败继续定位：怎么更可靠地使用证据编号，怎么稳定遵守场景结构，怎么把用户陈述用于分析又不伪装成文档证据。这里写的是待解决的问题，并不是它们已经得到修复。

这轮9次模型调用的费用上界为0.115106元。加上前几轮的费用上界和仍保留的未知预留，累计占用0.502344元，5元授权还剩4.497656元；累计调用28/36次，还剩8次。这是保守预算记录，不是供应商实际账单。

我原本希望这轮能把最后一道题补齐，结果反而退回了0/3。这个结果不太好看，但它比只挑一个走通的中间步骤来展示更能说明现在的问题。

我会把原始回答、工具轨迹、修改前代码和失败原因一起保留。等完整任务确实跑通，再讨论它做得好不好。
