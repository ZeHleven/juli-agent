# 据理首轮真实模型评测资料（v1）

日期：2026-10-02。**资料已准备不代表 Agent 已通过评测。本目录不调用模型，所有真实运行、分数、耗时与费用尚未产生。**

本套资料包含 12 道基础题和 4 道配对变体。岗位匹配与招投标属于开发集；课程选择用于观察新场景的迁移表现。所有人物、机构、课程和项目条件都是虚构的，招投标条件是材料自定规则，不代表真实采购法规或法律意见。

## 从哪里开始

- [案例导航](CASEBOOK.md)：按题目点击打开输入资料和对应评分卡，适合先人工浏览。
- [案例清单](suite.json)：问题、判断日期、上传文档清单、资料角色及评分文件位置。
- [验收标准](rubric.md)：逐项计分、硬性失败、追问闭环和错误归因方法。
- [评分表模板](grader/scorecard-template.json)：当前所有结果为空，真实运行后逐题填写。
- [原文证据索引](grader/evidence-index.json)：每条评分事实的原文、文件哈希、行号和字符位置。
- [静态检查记录](fixture-checks.json)：仅检查资料结构、可定位引用、文本解析与场景兼容性。
- [冻结清单](freeze.json)：样本、评分标准和场景文件的 SHA-256，后续修改需要新版本。

`grader/` 是评审专用材料，包含答案范围和用户回答卡。不得作为用户背景、问题附件、场景指导或模型工具结果上传。`suite.json` 也不能整份发送给被测模型，因为其中含题型、分组和评分文件位置。

未来执行时仅从选定案例提取 `question`、`as_of_date`、`documents` 中列出的文件、显示名称和资料角色；使用 `scenario_path` 指定的受信场景包。上传必须是清单白名单，不能递归上传这个目录。不要把题型或正确答案放进资料名称。当前尚未实现自动真实模型评测执行器。

## 分组与首轮顺序

每个场景的 01–04 分别覆盖资料充分、关键缺失、资料冲突、长文关键条件。岗位与招投标的 05 是仅修改关键条件的变体，06 是只改无关内容或顺序的变体，与 01 比较；不要求模型采用相同措辞、引用 ID 或调用顺序。

先从开发集的 `career-01`、`career-02`、`tender-03` 做三题连接与交互检查；固定模型、配置、输入和预算后，再决定整套运行。计划每题独立运行三次，但本轮实际运行次数为零。16 题全部重复三次是 48 个任务，每个任务可能含多次模型 API 调用，不能把任务数当调用次数或费用上限。

课程选择是**预留验证集**：开发者已编写并审阅，文件在本地可见，不能称作独立盲测。不要在调试岗位和招投标时利用课程评分答案改善提示词。若使用了课程题的结果调整实现，需把它们转入开发集，并在实现冻结后重新编写未参与调试的题。

## 问答操作

需要追问的案例在对应评分文件中有 `answer_facts`。操作者按模型实际问到的主题提供相应答案；一次问多个相关主题可一并回答。只问无关问题时，不主动补上关键答案来帮助通过。若问题含糊但可合理理解，记录原问题与对应回答依据，不用逐字匹配问题文本判错。

资料充分时不强制追问。缺失或冲突场景允许先给条件性分析，但需要指出关键缺口并请求确认；只在最终报告中列问题，不等于完成交互式追问。回答后要复核结论是否更新、是否重复追问，以及是否把用户陈述错误包装为文件已证明的事实。

## 复核命令

在仓库根目录、已安装开发依赖的环境中执行：

```bash
python tools/check_quality_suite.py
```

命令不会读取凭据、连接模型、初始化数据库或给 Agent 打分。它核对文档角色、场景包、每条证据原文、长文位置和冻结哈希。`--freeze` 只用于首次生成清单，已有冻结文件时拒绝覆盖。修订应建立新版本，不在已有模型结果旁偷偷改答案。

## 本轮覆盖范围

首版正文是 UTF-8 Markdown，长文超过单片段长度；静态检查使用正式文本解析器。没有 PDF、DOCX、扫描件、OCR 或真实用户文档的表现结论，也未测试界面、并发、取消恢复、跨空间授权或恶意文档诱导。这些需在后续格式与运行边界专项补充，不能由本目录通过推断。

本轮未改动 Agent 运行器、默认提示词、工具权限或正式场景包。课程场景仅放在本评测目录，后续由部署者显式加载，不进入默认场景目录。本次只做本地交付，尚未提交或推送这些评测材料。
